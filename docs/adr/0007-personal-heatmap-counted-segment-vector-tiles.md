# 0007. Personal Heatmap as Counted-Segment Vector Tiles Built on Request

Status: superseded in part by ADR-0008. Its tile format, "full heat" scale endpoint and browser-side colouring are replaced by raster density tiles in [ADR-0008](0008-personal-heatmap-raster-density-tiles.md). The heatmap route storage, heatmap revision, Heatmap Filter, caching and renderer strategy still stand.

A Heatmap is served as Mapbox Vector Tiles that PostgreSQL builds on request (`ST_AsMVT`). Each tile is made from routes that were simplified in advance for each zoom band. The routes are snapped to a coarse grid, about 4 screen pixels per cell and never finer than about 10 m on the ground, and each snapped segment carries the number of distinct Activities that cross it. Tiles carry no Activity ids. The browser turns that count into colour and glow on a log scale. The scale's "full heat" value is the ~95th-percentile count for each zoom band, measured across the whole filtered Heatmap. Tiles are cached only by the browser: their URL contains the athlete's heatmap revision and the Heatmap Filter, and they are served `private, immutable`. The "full heat" scale response is keyed and cached the same way, by revision and Heatmap Filter, as immutable. We chose this because it keeps any Heatmap Filter (an arbitrary date range or set of sports) cheap at every zoom, keeps the JVM out of geometry processing, and keeps server memory flat, while still producing Strava-style density curves.

## Considered Options

- **Overlap glow (all matching routes sent as see-through lines)**: Rejected. MapLibre has no additive blending, so brightness tops out after a few overlaps and a road run hundreds of times cannot be told apart from one run five times.
- **Precomputed density aggregates**: Rejected for v1. They only serve the filters they were built for, so arbitrary date ranges would need a cube per sport and month or a slower fallback anyway. We will reconsider only if measured tile times miss their targets.
- **Raster density tiles**: Not chosen for v1, but kept possible by a renderer strategy (see Consequences).
- **Scale relative to the current view**: Rejected. A lone Activity in an otherwise empty area would show at full heat. The athlete's whole filtered Heatmap has to decide what "hot" means.
- **Scale relative to each tile**: Rejected. Neighbouring tiles disagree on what "hot" means, which leaves visible seams.
- **Revision counter on the athlete's user row**: Rejected. `UPDATE … SET rev = rev + 1` holds a row lock until commit. Parallel Import Batch workers for one athlete would queue on it, and it adds a new lock to the deadlock-prone ordering described in ADR-0006 (issues #98, #102).
- **Server-side tile cache (Redis)**: Rejected for v1. Immutable URLs that carry the revision already make the browser cache correct, and a server cache would grow server memory with every athlete × filter × tile. We will add one only if measured cold-tile times call for it.

## Consequences

- Each Activity with a route has one heatmap route row. The row holds the route in Web Mercator, split wherever consecutive points jump further than a per-sport threshold, and simplified once per zoom band. It also copies the Activity's athlete, sport and start time, so a tile query filters and looks up locations in one table with no join. `ActivityDetailsRepository.upsert` writes the row in the same statement as the Activity Details, and the delete cascade removes it. Single and batch sport edits recompute the row, not just its copied sport, because the split threshold depends on sport. The import budget is about 5 ms per Activity.
- One SQL function derives the row from a route and a sport. It is the single source of truth for splitting and simplification: import, sport edits and backfill all call it.
- Existing Activities get their rows from a Flyway migration that applies the same SQL function. If tolerances change later, a new migration recomputes every row.
- Every write to a heatmap route row stamps it with a fresh value from a PostgreSQL sequence, which takes no lock. The athlete's heatmap revision is the pair (number of rows, highest stamp), read from an index on (athlete, stamp). Any insert, edit or delete changes that pair.
- Tile rendering is a strategy behind `HeatmapTileRenderer` (`render(athlete, filter, tile) → bytes + media type`), chosen by the `stridehearth.heatmap.renderer` property. `GET /api/heatmap/renderer` tells the SPA which renderer is active and gives its tile URL template, and the SPA pairs it with a matching `HeatmapLayer` adapter. That adapter is the only code that touches MapLibre for the heatmap. The "full heat" scale endpoint belongs to the counted-segment renderer, not the shared core. v1 ships exactly one renderer on each side.
- Tiles are generated up to zoom 16, and MapLibre enlarges the zoom-16 tiles beyond that. From zoom 13 up, the scale reuses the z10–12 reference instead of scanning full-detail routes.
- A `performanceTest` Gradle task, which is not part of `check`, seeds about 10k synthetic Activities. It measures cold tiles at z3, z8 and z14, the scale endpoint and the import cost, and compares renderer variants through `HeatmapTileRenderer`. `check` runs a small smoke version of it to catch index or query-plan regressions. Targets: under 300 ms at p95 for a cold tile and under about 500 KB per tile after gzip, at any zoom.
