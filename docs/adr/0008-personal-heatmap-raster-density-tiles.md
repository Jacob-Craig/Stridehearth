# 0008. Personal Heatmap as Raster Density Tiles

Status: accepted. Supersedes the tile format, scale and rendering decisions of ADR-0007 (counted-segment vector tiles). ADR-0007's heatmap route storage, heatmap revision, Heatmap Filter, caching and renderer strategy still stand.

A Heatmap tile is a 512-pixel PNG, rendered on request. For each tile, PostgreSQL reads the athlete's matching heatmap routes for the tile's zoom band and returns them clipped to the tile, in tile pixel coordinates. The JVM draws each Activity once, antialiased, into a mask and adds the masks together, so every pixel holds the number of distinct Activities that pass through it. A Gaussian blur of that density makes the glow, and a log scale against the **Full Heat** colours it from dim red through orange and yellow to white. We chose this because it is the only approach we tried that gives the Strava look: overlapping passes really do add up, and GPS drift widens into a soft corridor rather than splitting into parallel strands.

The Full Heat is the ~95th-percentile number of distinct Activities on a snapped route segment for the tile's zoom band, across the athlete's whole filtered Heatmap. It is counted in SQL on the same coarse grid ADR-0007 used for drawing, and from zoom 13 up the z10–12 value is reused. Each heatmap route row stores its distinct snapped segments per band as numbers, in generated columns worked out when the row is written (V15), so counting is a `GROUP BY` with no geometry work. About one segment in eight, chosen by a fixed hash of the segment, is stored apart as a sample; a sampled segment is sampled for every route, so its count is exact. A Heatmap with fewer than 300,000 route-segment passes is counted exactly; a larger one is counted on the sample alone, which put the 95th percentile on the same value at 10,000 Activities. It is never less than 4 Activities: on a small Heatmap whose routes barely overlap, the 95th percentile is 1 to 3, and a road run two or three times would glow white-hot as if it were a habit. The floor also keeps the Full Heat above one Activity, which the log scale needs. Because it depends only on the heatmap revision and the Heatmap Filter, which are already in the tile URL, tiles stay `private, immutable`.

## Considered Options

- **Counted-segment vector tiles (ADR-0007)**: Rejected after a manual check on real routes. Snapping the drawn geometry to a grid of about 10 m split busy roads into parallel strands of low count, and drew a visible lattice of squares and diagonals at street zoom, especially past zoom 16. MapLibre has no additive blending, so the browser cannot recover a density picture from vector lines.
- **Raster density built in PostgreSQL (`postgis_raster`)**: Rejected. It has no antialiased line drawing or cheap blur, so the result looks pixelated and the blur (`ST_MapAlgebra`) is slow.
- **Colouring in the browser**: Rejected for v1. MapLibre cannot recolour raster tiles, so the colour ramp and the Full Heat are applied on the server.
- **Full Heat from a percentile of raster density**: Rejected. It would mean rendering the athlete's whole Heatmap at a reference zoom for each filter, while the SQL segment count is a single statement and measures the same thing closely enough.

## Consequences

- **CPU on the server.** The JVM now handles geometry, which ADR-0007 avoided: drawing, blurring and PNG encoding are CPU-bound. Memory stays flat, at about 1 MB of working buffers per tile while it is drawn, but a zoomed-out tile over thousands of Activities draws thousands of routes. The performance harness measures CPU time per tile and concurrent load against the existing targets: under 300 ms at p95 for a cold tile, and under about 500 KB per tile.
- **The Full Heat is cached; tiles are not.** Counting it reads the athlete's whole filtered Heatmap. With the stored segments that takes up to about 100 ms at 10,000 Activities, against 1 to 10 seconds when every route was snapped per count, but it is still too much to repeat for every tile, so the server keeps it in a small bounded in-memory map keyed by athlete, heatmap revision, Heatmap Filter and zoom band. The revision in the key keeps it correct by construction. This is one number per key, not a tile cache.
- **Segments are stored for the Full Heat.** Each heatmap route row carries six `bigint[]` columns, its snapped segments per measured band, sampled and not, about 2 KB for a 10 km run. They cost about 0.5 ms per 10 km of route on write, and changing the grid or the sample means a migration that recomputes them.
- **No counts in the tile.** Hover can no longer show "N Activities". It is left out of v1. A later endpoint that counts the Activities near a point could add it without changing tiles.
- **Look changes are server changes.** The palette, line width and glow live in the renderer. Browsers keep immutable tiles for a year, so the tile URL template carries a renderer version, and any change to the look bumps it.
- **One-pixel bands and palette tiles (#119).** From zoom 13 up, each zoom has its own stored band, simplified to about one pixel at that zoom; the full-detail band (`geom_z16`) also finds a tile's routes by bounding box. Tiles are 8-bit palette PNGs (31 heat levels × 8 opacities), about a fifth the size of 32-bit ones.
- **Starting View (#108).** The starting-view endpoint returns the bounds of the busiest area, not of every route, so an athlete who trained on two continents does not open on the whole world. Each matching route falls in a 25 km Web Mercator grid cell by the centre of its bounding box; an area is a cell and its eight neighbours, ranked by route count with the more recently used area winning a tie. The browser keeps a Remembered View per athlete in local storage, which beats the Starting View, but only while there are routes to show. A new heatmap revision refetches the Starting View as well as moving the map to new tiles, so the empty state clears once the first routes arrive.
- **One renderer.** v1 ships exactly one renderer on each side: the raster density renderer and its `HeatmapLayer` adapter. The counted-segments renderer is removed, and its segment counting survives only to measure the Full Heat.
- The prototype that settled this is kept on the `prototype/105-raster-heatmap` branch, with the three variants compared on `/heatmap?variant=`.
