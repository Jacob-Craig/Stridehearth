# 0003. Best Efforts and Personal Records Engine

Status: superseded in part by ADR-0006. The "Concurrent Ingestion" claim below, that atomic `INSERT ... ON CONFLICT` alone removes lost Personal Record updates, is replaced by [ADR-0006](0006-serialise-personal-record-writes-per-athlete-and-sport.md). Every other decision still stands.

Personal record and best effort detection runs in-memory during activity ingestion using an $O(N)$ two-pointer sliding window with boundary linear interpolation over primitive telemetry arrays, persisting results to `activity_best_effort` and updating a dedicated `user_personal_record` summary table. This architecture guarantees sub-millisecond $O(1)$ dashboard reads, accurate sub-second timing independent of GPS sampling frequency, and resilient consistency during historical backfills and activity deletions.

## Considered Options

- **On-Demand SQL Scanning & Aggregation**: Computing best efforts dynamically when rendering activities or user dashboards. Rejected because scanning dense telemetry arrays (`t` and `distance` arrays with thousands of entries) across multiple benchmark windows and hundreds of activities per athlete causes severe read latency, high database CPU utilization, and unpredictable page load times.
- **Materialized `is_pr` Boolean on `activity_best_effort`**: Marking records directly with an `is_pr` flag. Rejected because importing historical activities out of chronological order or deleting/re-importing activities requires complex multi-row cascading updates and risks data drift.
- **Discrete Sample Snapping (No Boundary Interpolation)**: Calculating best efforts using only recorded sample boundaries without interpolation. Rejected because GPS watches record with varying intervals (1-second smart recording vs. sensor drops), which artificially distorts times for standard benchmarks (e.g. 400m, 1k, 1mi, 5k, 10k, Half-Marathon).
- **Moving Time vs. Wall-Clock Elapsed Time**: Stitching together non-continuous movement intervals by subtracting pauses. Rejected because standard athletics rules and endurance platforms (World Athletics, Strava) require continuous wall-clock time across the window, ensuring stopped rest periods cannot artificially inflate performance.

## Consequences

- **Domain Model & Terminology**: Adopts **Benchmark Distance** (standardized target distance), **Best Effort** (peak continuous window for a benchmark in an activity), **Personal Record** (athlete's all-time #1 Best Effort per benchmark and sport), and **Dashboard** (the athlete's primary landing view at `/dashboard` summarizing Personal Records and training metrics). Rejects "segment" to avoid confusion with geographic course segments.
- **Predefined Benchmark Set**: Initial scope targets `ActivitySport.RUN` with standard metric distances: 400m (400.0m), 1k (1,000.0m), 1 mile (1,609.344m), 5k (5,000.0m), 10k (10,000.0m), and Half-Marathon (21,097.5m). Benchmarks are keyed by sport to support future disciplines (cycling, swimming).
- **Sliding Window Algorithm**: Executes directly against in-memory `FitTelemetry` primitive arrays during ingestion before database commit. When FIT files omit per-record cumulative `distance`, `FitTelemetryMapper` synthesizes cumulative meters in an $O(N)$ pass using Haversine great-circle distance between consecutive GPS fixes and falling back to `(enhancedSpeed ?: speed) * dt` across non-GPS intervals. A two-pointer sliding window traverses monotonically non-decreasing distance arrays in $O(N)$ time per benchmark. Linear interpolation estimates exact boundary fractional timestamps.
- **Persistence Schema (`V10__create_activity_best_efforts.sql`)**:
  - `activity_best_effort`: Stores `activity_id`, `sport`, `benchmark_distance`, `elapsed_time_seconds`, `start_index`, `end_index`, `start_time_seconds`, `end_time_seconds`, `start_distance_meters`, `end_distance_meters`. Exactly one peak record per benchmark distance per activity.
  - `user_personal_record`: Stores `(user_id, sport, benchmark_distance)` referencing `best_effort_id`, `activity_id`, and cached `elapsed_time_seconds` for immediate $O(1)$ Dashboard reads (`idx_user_personal_record_user_sport`).
- **Concurrency, Tie-Breaking & Consistency Handlers**:
  - **Tie-Breaking Rule**: The earliest activity (`started_at ASC, activity.id ASC`) to achieve a benchmark time holds the Personal Record; a subsequent effort must be strictly faster (`elapsed_time_seconds < existing`) unless imported with an earlier `started_at` at the exact same elapsed time.
  - **Concurrent Ingestion (Single & Bulk Import)**: Workers evaluate newly saved `activity_best_effort` rows using deterministic `BenchmarkDistance` ordinal ordering and atomic PostgreSQL `INSERT ... ON CONFLICT (user_id, sport, benchmark_distance) DO UPDATE` statements, eliminating read-modify-write race conditions (lost updates) and row-lock deadlocks across parallel `BatchImportWorker` threads. _Superseded in part by ADR-0006: `ON CONFLICT` alone does not stop a full recalibration from overwriting a concurrently imported faster Personal Record, so every Personal Record write is also serialised per athlete and sport._
  - **Activity Deletion, Upgrade & Sport Reclassification**: Foreign keys (`ON DELETE CASCADE`) automatically remove invalidated `activity_best_effort` and `user_personal_record` rows. A single set-based PostgreSQL query (`INSERT INTO user_personal_record ... SELECT DISTINCT ON (abe.benchmark_distance) ... ORDER BY abe.benchmark_distance, abe.elapsed_time_seconds ASC, a.started_at ASC, a.id ASC ON CONFLICT DO UPDATE`) atomically recalibrates the athlete's Personal Records from remaining efforts. Reclassifying an activity to `RUN` scans stored `activity_details` telemetry (`t` and `distance` arrays) and updates `activity_best_effort` and `user_personal_record`.
  - **Backfill**: An idempotent per-athlete service re-scans existing activities with telemetry, committing one page of Activities per transaction (see ADR-0006).
