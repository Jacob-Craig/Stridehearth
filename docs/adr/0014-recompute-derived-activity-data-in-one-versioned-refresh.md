# 0014. Recompute Derived Activity Data in One Versioned Refresh, Backfilled by a Background Worker

Status: accepted.

Derived Activity data (Grade-Adjusted Pace first, then the run metrics, Training Load and peaks that later issues add, and every Activity's temperature and Mean Altitude, ADR-0017) is computed by one module, `DerivedDataRefresh`, in one pure pass (`ActivityAnalysis.analyse`: Telemetry Cleaning per ADR-0013, then each analytic over the Cleaned Activity Details). It is stored in `activity_derived_metrics`, which holds **one row for every Activity of every sport, MANUAL included**. A column that does not apply to an Activity (GAP for a Ride, anything for an Activity without Activity Details) is NULL; the row itself is never missing. Each row records the `algorithm_version` that computed it, so the table is a ledger of what has been computed: `DERIVED_DATA_VERSION` rises whenever any of the algorithms would compute different values from the same Activity Details (issues #26, #32). Data with many rows per Activity, such as a Run's Peak Efforts (#38, `activity_peak_effort`), lives in its own table that the same refresh replaces in the same pass; the Activity's `activity_derived_metrics` row stays the ledger of the version it was computed at.

Writers call the refresh synchronously, in their own transaction, whenever an input changes: an Activity is created (with or without Activity Details, so even a create without them gets its row), its Activity Details change (an Upgrade), its sport or `startedAt` is edited, or it is deleted. The refresh also marks the athlete's rollups (`AthleteRollups`, by the Activity's `startedAt` instant), which run once per transaction before commit (ADR-0016).

Activities without a row (imported before derived data existed) are filled in by a **Backfill**, and rows at an older `algorithm_version` are replaced by a **Recompute**. Both are done by `DerivedDataRecomputeWorker`, which a scheduled trigger runs every 15 s (a bounded number of pages per run). The candidates are "no row, or `algorithm_version < DERIVED_DATA_VERSION`", across every Activity.

## Considered Options

- **Delete the row when nothing applies (non-GAP sports, no Activity Details)**: Rejected. Without a row there is no ledger: a version bump could not find the Activities a later analytic (Training Load for every Activity, a reason why it is unavailable) must be computed for, and the candidate query would have to repeat every analytic's applicability rules, which is the endless-rescan problem of the Best Effort Backfill.
- **A one-off Backfill at startup**: Rejected (the #26 triage proposed it). A failed run waits for the next restart, which may be weeks away, and a version bump on a long-running Server would never be acted on. A recurring worker retries on its own and also serves the durable recompute requests later issues add.
- **A version-guarded write without row locks** (`INSERT ... WHERE stored version < new`): Rejected. It protects against a concurrent refresh, not against a concurrent sport edit or delete: the page's snapshot can still see the old sport, so a Ride could keep a GAP row, and a delete committing under the page's insert fails it with a foreign-key violation.
- **A Manage-page button or HTTP endpoint for the Backfill**: Rejected. Derived data must catch up without anyone asking, and the existing `POST /api/activities/backfill-best-efforts` is left as it is.
- **One refresh module per analytic**: Rejected. Each would re-read and re-clean the same Activity Details, and they could disagree about the cleaning version.

## Consequences

- Call-site order: the refresh runs directly **after** `BestEffortRefresh.refresh` and **before** heatmap and Activity History writes. It flushes the caller's pending change, and its insert takes a key-share lock on the Activity's row, which ADR-0006 orders after the Personal Record lock. It takes no lock of its own and writes no Activity History Entry.
- Each worker page is one transaction that first locks its Activities with `SELECT id FROM activity WHERE id IN (:ids) ORDER BY id FOR NO KEY UPDATE`, the lock an Upgrade's offer takes, then reloads them and refreshes. A page therefore waits for a concurrent edit, Upgrade or delete to commit and computes from what it committed; an Activity deleted meanwhile is skipped. Every write to an Activity's derived data is serialised by that Activity's row lock, so the refresh can write unconditionally.
- Batch edits and deletes take their Activities' row locks in ascending id order too: they delete, and record Activity History Entries, in id order, and `hibernate.order_updates` flushes updates by primary key. So a batch and a page wait for each other instead of deadlocking; a batch request is not retried, so it must not be the victim. They do not lock their rows up front, because ADR-0006 takes the Personal Record lock before any row lock. An import of a file with several sessions does lock up front: after the Personal Record locks of its already-imported Activities, it locks their rows in one statement in id order, before offering any of them Activity Details (which locks in session order), since an import is not retried after a deadlock either. A page that still loses a lock race (to any other writer) is retried up to three times; if it still fails, the run ends and the next run resumes.
- A page that fails any other way is retried one Activity per transaction, so a single Activity whose details cannot be analysed is logged and skipped instead of stopping the scan. It stays a candidate, but the worker remembers in memory when it failed and passes over it for an hour before analysing it again. Without that, once every other row is current, each 15 s run would be a pass of its own and would re-analyse the Activity twice and log two stack traces every run (about 5,800 runs a day); with it, a failing Activity costs one retry and one logged failure an hour until the cause is fixed. A restart, which is also how a fix or a version bump arrives, retries it at once. The worker keeps its place in memory: each run resumes after the last page the previous run finished and wraps around to the lowest id once, so failing Activities, however many, never use up every run's pages ahead of the Activities after them. A restart starts again from the lowest id.
- Once every row is at the current version, each run is one candidate query that finds nothing: an anti-join walking the primary keys of `activity` and `activity_derived_metrics`, linear in the number of Activities. That is accepted rather than remembering in memory that a version is caught up, because rows can go missing without a version bump (an Activity inserted by SQL, as the visual-check seeding does, or a row deleted by hand), and the durable recompute requests later issues add are served by the same runs.
- The worker shares Spring's single scheduler thread with the import batch reconciler and reclaimer, so each run is bounded (`stridehearth.analytics.recompute-pages-per-run`, 10 pages of 50) and a long catch-up spans several runs. After an upgrade that raises the version, derived data is briefly stale until the worker reaches it.
- The scheduled trigger is a separate bean guarded by `stridehearth.analytics.recompute.scheduled`; the worker itself is always present. Tests turn the schedule off (`src/test/resources/config/application.yaml`, which also applies to `TestStridehearthApplication`) and call `drain()` directly, scoped to their own athletes because test classes share one database.
- `AthleteRollups` is pulled forward from #36 (daily load and the PMC), deliberately: the one refresh calls its `mark*` API, so the call sites, and the refresh on a `startedAt`-only edit (which changes nothing derived until a rollup reads the day), are in place once, rather than each later issue reopening every writer. Since #36 its before-commit pass rebuilds Daily Load and the Performance Management Chart (ADR-0016); the peak marks' semantics stay provisional until #39 (Critical Speed) consumes them.
- Rollup marks are instants, not days: the conversion to the athlete's local day happens in the before-commit pass, so the skeleton needs no rework once athletes have a time zone. The daily-load mark keeps the earliest instant per athlete; the peak marks keep every instant, because a model fitted over a window is affected only near each change.
- The telemetry endpoint emits a derived stream only while it is parallel to `activity_details.t`, so a row computed from details since replaced never misaligns the charts.
- The Best Effort Backfill and its endpoint are unchanged; Best Efforts keep scanning the recorded distance (ADR-0013).

## Durable recompute requests (#35)

Training Load, and a Run's VO2max Estimate (#42, from the resting and max heart-rate Thresholds), also depend on the athlete's Thresholds as of the Activity's local date, which change without any Activity changing. A Threshold or Athlete Time Zone change therefore does not recompute anything in its own request. A plain listener in the writing transaction records a durable request in `athlete_analytics_state` (one row per athlete): `recompute_from` is the earliest affected local date, or NULL for everything, and `recompute_requested_at` stamps the request. A second request merges into a pending one: the earlier date wins, and NULL wins over any date. The request commits or rolls back with the change.

The worker serves pending requests first on each run, before the version Backfill and within the same page budget. For each athlete, it pages through their Activities with a local start date on or after `recompute_from`, in id order. It locks each page as it does for the version Backfill, and replaces only the threshold-dependent columns, the Training Load and the VO2max Estimate (`DerivedDataRefresh.refreshThresholdDependent`, `ThresholdDependentMetrics`). An Activity with no row, or a row at an older version, is left to the version Backfill or Recompute: the update matches only rows at the current version. When the pages run out, the request is cleared only if `recompute_requested_at` still equals the value read at the start (compare-and-clear), so a change that commits mid-run is served by the next run. It is also kept pending while any of its Activities was skipped because it failed or was backed off. Later runs retry only those Activities once their back-off has passed, and clear the request when none is left. A request larger than one run's pages resumes, through an in-memory cursor, where the last run stopped. A restart starts it again from the beginning.

Compare-and-clear alone does not cover an Activity write that is still in flight. An import, edit or reclassify may score a Training Load against the old Thresholds before a change commits. If a run then serves and clears the request before that write commits, its stale load is never revisited. A transaction-scoped advisory lock per athlete closes this gap:

- `DerivedDataRefresh` takes the shared side of the lock before it reads an athlete's Thresholds, and reads their time zone under it.
- `requestRecompute` takes the exclusive side.
- The change therefore either commits before the writer reads, so the writer sees the new values, or waits for the writer to commit, so its request covers the writer's Activity.
- Writers never block each other.
- The lock is taken after the Personal Record and Activity row locks (ADR-0006). A Threshold or zone change holds none of those, so it cannot deadlock with a writer.

- **Rejected: recompute synchronously in the Threshold request.** An athlete with years of history would hold one transaction over thousands of Activities, locking every one of their rows.
- **Rejected: an after-commit listener.** A crash between commit and recompute would lose the request. The durable marker survives restarts.

## Streams that depend on athlete-level models are computed on read (#40)

**Stamina** depends on the athlete's Critical Speed model as well as the Run's own Grade-Adjusted speed, and that model is refitted by the before-commit rollup whenever a Peak Effort in its 90-day window changes (ADR-0016). It is therefore not part of this refresh and not stored: `StaminaService` integrates it on every read of the telemetry endpoint (`derivedStreams.staminaPct`) and of the Activity (`minStaminaPct`), from the stored `gap_speed` and the model in effect on the Run's athlete-local date.

- Storing it would make the rollup rewrite other Activities' rows. The rollup writes only athlete-keyed rows, because a write to a row referencing an Activity takes a key-share lock that can deadlock with a concurrent delete of that Activity.
- The integration is O(N) in the samples and needs no migration, version bump or Backfill; a refit simply changes the next read.
- The model is the one dated the Run's own day, so the Run's own Peak Efforts count towards it: a breakthrough Run is measured against the model it set, not one fitted before it. This keeps one model per day for every consumer rather than a second, Run-excluding fit.
- **Rejected: storing the stream with the model inputs it used, recomputed after each refit.** It bounds the cascade, but it still writes Activity rows from the rollup, and it adds a column set and a recompute path for a value that is cheap to compute.
